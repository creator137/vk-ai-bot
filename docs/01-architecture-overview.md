# Architecture Overview

## Architectural style

Проект реализуется как модульный монолит.

Причины выбора:

- быстрее и дешевле для MVP
- проще сопровождать
- достаточно гибко для дальнейшего роста
- не требует преждевременной микросервисной сложности

## High-level modules

### 1. VK Transport

Отвечает только за:

- прием входящих событий от VK
- валидацию и нормализацию payload
- передачу команды в application/service layer
- отправку ответа обратно в VK

VK transport не должен содержать:

- бизнес-логику подписок
- бизнес-логику кредитов
- прямую работу с AI-провайдерами
- прямую логику платежей

### 2. Users

Отвечает за:

- поиск/создание пользователя
- профиль пользователя
- связь internal user <-> VK user

### 3. Billing

Отвечает за:

- создание платежей
- хранение платежей
- прием webhook от платежных провайдеров
- верификацию webhook
- безопасную идемпотентную обработку платежей

### 4. Subscriptions / Wallet / Access

Отвечает за:

- тарифы
- подписки
- кредиты
- проверку доступа
- списание кредитов
- выбор источника списания

### 5. AI Layer

Отвечает за:

- единый интерфейс к AI-провайдерам
- маршрутизацию по capability/model alias
- нормализацию ответов и ошибок
- изоляцию внешних API от бизнес-логики

### 6. Conversations

Отвечает за:

- историю запросов
- историю ответов
- хранение минимального контекста
- связь запроса с usage и billing

### 7. Attachments

Отвечает за:

- прием изображений
- проверку типа и размера файлов
- временное хранение
- передачу в AI layer
- очистку временных файлов

### 8. Workers

Отвечает за:

- тяжелые AI-задачи
- ретраи
- постобработку
- очистку временных данных
- фоновые операции, не требующие выполнения в HTTP request lifecycle

## Core architecture rules

### Thin routes

Routes/handlers должны быть тонкими.
Они только:

- принимают запрос
- валидируют вход
- вызывают service layer
- возвращают ответ

### Business logic in services

Вся бизнес-логика должна жить в service layer.

### Persistence via repositories

Работа с БД должна идти через repository layer или аккуратно выделенные data access objects.

### External integrations via adapters

Интеграции с:

- AI providers
- payment providers
- VK APIs

должны быть изолированы в adapters/providers.

## Data flow examples

### User request flow

1. VK отправляет событие
2. VK transport принимает и валидирует событие
3. Users service находит или создает пользователя
4. Access engine проверяет право доступа
5. Если доступ есть — создается задача на обработку
6. Worker или service вызывает AI provider adapter
7. Ответ сохраняется
8. Ответ уходит обратно пользователю

### Payment flow

1. Пользователь выбирает тариф/пакет
2. Billing service создает payment entity
3. Payment adapter создает платеж у провайдера
4. Пользователь оплачивает
5. Платежный провайдер отправляет webhook
6. Billing module валидирует и идемпотентно обрабатывает webhook
7. Выдается подписка или начисляются кредиты
8. Событие фиксируется в БД и логах

## Access model

Система поддерживает:

- подписки
- кредиты

Рекомендуемый порядок проверки:

1. есть ли активная подписка
2. покрывает ли подписка данный сценарий
3. есть ли доступные лимиты/кредиты
4. если нет — предложить оплату

## AI abstraction

Пользовательский интерфейс не должен быть намертво привязан к реальным внешним названиям моделей.

Предпочтительно использовать внутренние capability aliases, например:

- basic_text
- smart_text
- vision_text

Это позволяет менять провайдеров и модели без ломки продукта.

## Async and workers

Тяжелые операции не должны выполняться прямо в webhook/request, если это может ухудшать стабильность.

Через workers выносятся:

- тяжелые AI запросы
- multimodal/vision обработка
- retries
- фоновые очистки
- постобработка

## Deployment

Для MVP используется Docker Compose.

Основные контейнеры:

- api
- worker
- postgres
- redis
- nginx

## Guiding principle

Система должна быть простой для MVP, но не хаотичной.
Любое решение должно быть:

- достаточно надежным
- достаточно понятным
- не перегруженным
- пригодным для продолжения разработки двумя разработчиками
